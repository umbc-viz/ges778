17. Alternative geographies & manipulation

Author

Camille Seaberry

Modified

November 24, 2026

Normally when you’re mapping data, you’re stuck with wherever your locations are or how they’re shaped. And that’s often the case, and should still be what anchors your work. But there are ways that you might manipulate the way locations and areas are represented. They run a wide gamut from somewhat artsy but legible to weird, squishy, and hard for most people to read.

Borders aren’t real

When we’re talking about manipulating geographies, we should start with thinking about the fact that (most) borders aren’t real! We’ve used census tracts a bunch, which are generated by bureaucrats every 10 years and aren’t something you can see in the real world. Even the definition of a block from the Census Bureau can change. Sometimes boundaries are defined by natural physical features like rivers, but these change over time as well.

At some point, you’ll probably run into a situation where the definition of the place you’re mapping is called into question. It can be something simple, like disagreements over the borders of a neighborhood, or what constitutes Baltimore’s downtown. I feel like a dork every time I make a map of New Haven with my old neighborhood labeled with the name the city government uses but not people in the neighborhood. Even what a neighborhood is and what it does is subjective, as explored in Wood (1974). It can be something way bigger than the project you’re working on, such as when a developer releases mapping software and, because of the default shapefile they’ve used for demos, is accused of picking sides in an international territory conflict. Places get renamed, renames get undone, and mapping platforms are split on whether the Gulf of America exists.

Wood, D. (1974). A neighborhood is to hang around. Children’s Environment Quarterly, 1, 29–35.

All that is to say that we can and should critique the boundaries of what we’re mapping, and think about whether they serve our purposes well. In my experience, a lot of the time they don’t, but they’re the best and most commonly-understood we’ve got.

Using standard geographies

To get started, here’s our normal choropleth of percentage of adults 25+ with a graduate degree by county.

Code 
# just to have an example of a count instead of rate, calculate number of people with grad degrees
grad_degrees <- counties_sf |>
    dplyr::left_join(justviz::acs, by = "name") |>
    dplyr::mutate(n_grad_degree = round(grad_degree * ages25plus))

ggplot(grad_degrees) +
    geom_sf(aes(fill = grad_degree), color = "gray20", linewidth = 0.2) +
    scale_fill_fermenter(palette = "RdPu", direction = 1) +
    labs(
        title = "Share of adults with graduate degrees,\nMaryland adults 25+ by county, 2024"
    ) +
    coord_sf(ndiscr = 0)

This shows high shares of adults having graduate degrees in Howard and PG Counties, and lower rates in more rural areas in Western Maryland and the Eastern Shore.

Bubble maps

We’ve talked about how there are lots of problems with choropleths, biggest among them being the way they conflate land area with whatever data you’re mapping. One easy alternative is to place a bubble sized with the area (not radius!) based on a numeric value in your data. Usually this involves putting a circle on each area’s centroid.1 These can work well for things that aren’t appropriate for a choropleth, such as counts instead of rates, especially counts of something relatively rare where a single additional event could throw off the rate of a small area (that’s the main time I’ve used them, things like drug overdose deaths).

1 There are some different algorithms you can explore for defining the center of a region, since common definitions of a centroid can actually fall outside the polygon. You also might try schemes to weight the centroid to be more of a center of population mass than just a center of land mass. (example)

Code 
# draw county boundaries, then draw points at their centroids
grad_cents <- sf::st_centroid(grad_degrees)

ggplot(grad_degrees) +
    # layer for boundaries
    geom_sf(color = "gray20", linewidth = 0.2) +
    # layer for bubbles
    geom_sf(
        aes(size = n_grad_degree),
        data = grad_cents,
        color = seq_pal[5],
        alpha = 0.8
    ) +
    # make sure to scale by area, not radius
    scale_size_area(
        max_size = 10
    ) +
    labs(
        title = "Number of people with graduate degrees,\nMaryland adults ages 25+ by county, 2024"
    ) +
    coord_sf(ndiscr = 0)

You could also do a hybrid, where the bubbles’ sizes are scaled to counts and the colors are scaled to rates, but it’s hard to make that not look cluttered.

Code 
ggplot(grad_degrees) +
    # layer for boundaries
    geom_sf(color = "gray20", fill = "gray95", linewidth = 0.2) +
    # layer for bubbles
    geom_sf(
        aes(size = n_grad_degree, fill = grad_degree),
        data = grad_cents,
        # color = seq_pal[5],
        alpha = 0.8,
        linewidth = 0.05,
        shape = 21
    ) +
    # make sure to scale by area, not radius
    scale_size_area(
        max_size = 10
    ) +
    scale_fill_fermenter(palette = "RdPu", direction = 1) +
    labs(
        title = "Number & share of people with graduate degrees,\nMaryland adults ages 25+ by county, 2024"
    ) +
    coord_sf(ndiscr = 0)

I’m sure someone likes this, but it’s not me. Note how to do with very light bubbles I’ve had to add an outer stroke to the bubbles (switched the shape to 21, which is a filled circle), but for counties with very small counts and rates, the outline starts to obscure the data. I also had to adjust the fill of the polygons to improve the contrast.

Adjusting choropleths

Dasymetric maps

Dasymetric mapping is a technique where you adjust a choropleth so the shaded areas more closely match where within a polygon people actually live. This is often done with land cover data or population rasters, so that areas where people don’t generally live can be subtracted from the polygons to be shaded. I haven’t had a need to make one, and I think my usual audience might be confused by it. But they can be very pretty, and if you have a use case, they’re probably worth the computational effort. There are some tools to make the calculations easier, such as a toolkit from the EPA, and examples of doing similar maps in the sf docs.

Incorporating population

An easier alternative is to make a choropleth like normal, but scale the opacity of regions based on population (or households). I noticed during the midterm elections that some newsrooms were doing this instead of the usual bright red vs bright blue maps of how land supposedly voted.

Code 
ggplot(grad_degrees) +
    geom_sf(
        aes(fill = grad_degree, alpha = total_pop),
        color = "gray20",
        linewidth = 0.2
    ) +
    scale_fill_fermenter(palette = "RdPu", direction = 1) +
    scale_alpha_continuous(
        range = c(0.3, 1),
        guide = guide_legend(
            override.aes = list(fill = seq_pal[5]),
            reverse = TRUE
        )
    ) +
    labs(
        title = "Share of adults with graduate degrees,\nMaryland adults 25+ by county, 2024"
    ) +
    coord_sf(ndiscr = 0)

Now we can see that even though both Howard & PG Counties fall into that highest bracket of shares, the number of people with graduate degrees will be different because PG County has about 3 times the population of Howard. You could (should?) scale opacity by population 25+ rather than total population like I did here.

I tried to build a broke geographer’s dasymetric map by cutting out blocks with no population. It’s…not worth the compute effort.

Changing shapes

Cartograms

A cartogram is like a choropleth, but the shapes have been distorted to account for the effect of different area sizes on how you view the choropleth, such as scaling area proportional to population. The downside is they’re hard to read for a place you’re not very familiar with, so I mostly only see them done well for something like the US by state, or the world by country. They look like choropleths drawn on Silly Putty and then squeezed. I have a running joke at work that one day when my boss isn’t paying attention, I’ll sneak a cartogram into one of our publications.

Code 
# the cartogram package has 3 different algorithms for creating cartograms
# returns an sf object, requires input be projected
# could instead scale by pop 25+
grad_degrees |>
    sf::st_transform(3857) |>
    cartogram::cartogram_cont(weight = "total_pop") |>
    ggplot() +
    geom_sf(aes(fill = grad_degree)) +
    scale_fill_fermenter(palette = "RdPu", direction = 1) +
    labs(
        title = "Share of adults with graduate degrees,\nMaryland adults ages 25+ by county, 2024",
        subtitle = "Shapes sized by total population"
    ) +
    coord_sf(ndiscr = 0)

Not a lot of people are going to know Maryland counties well enough to know what’s going on here.

An alternative is a Dorling cartogram, which replaces the polygon oozing effect with a circle packing algorithm.

Code 
grad_degrees |>
    sf::st_transform(3857) |>
    cartogram::cartogram_dorling(weight = "total_pop") |>
    ggplot() +
    geom_sf(aes(fill = grad_degree)) +
    scale_fill_fermenter(palette = "RdPu", direction = 1) +
    labs(
        title = "Share of adults with graduate degrees,\nMaryland adults ages 25+ by county, 2024",
        subtitle = "Shapes sized by total population"
    )

Again, not great for counties, but works okay for something like states across the country.

Geofacets

Geofacets are a version of small multiples where the panels are placed based on geographic locations. NPR’s data viz people seem to like these. Like the cartogram, these are best used for very familiar geographies. You can get grids premade from the geofacets package2, including states in the US and counties in some large states (including MD).

2 As of late 2026, there’s a year-old bug in the CRAN version of this package, so install from Github: remotes::install_github("hafen/geofacet")

Code 
library(geofacet)

justviz::acs |>
    dplyr::filter(level == "county") |>
    dplyr::select(name, less_than_high_school:grad_degree) |>
    tidyr::pivot_longer(
        -name,
        names_to = "edu",
        values_to = "share",
        names_ptypes = list(edu = factor())
    ) |>
    dplyr::mutate(
        name = name |>
            stringr::str_remove(" County") |>
            stringr::str_replace(" city", " City")
    ) |>
    ggplot(aes(x = edu, y = share, fill = edu)) +
    geom_col() +
    scale_fill_manual(values = qual_pal) +
    scale_x_discrete(labels = NULL) +
    geofacet::facet_geo(vars(name), grid = "us_md_counties_grid1") +
    theme(panel.grid.major.x = element_blank(), legend.position = "bottom") +
    labs(
        title = "Educational attainment, Maryland adults ages 25+ by county, 2024",
        x = NULL,
        y = NULL
    )

You can make custom grids too, using geofacet::grid_auto and the developer’s app for tweaking your grid. This lets you do something like make a grid of city neighborhoods.

Creating new shapes

We’ve done a bit of this in a lab already, but sometimes what you want to study is how two things relate to each other within space. One example I’ve mentioned is measuring accessibility of resources by counting the number of bus stops within a small, walkable radius of a location. These buffers might be arbitrary: in this case, my client decided a quarter mile was a reasonable distance for a parent and kid to walk from a bus stop to a daycare provider. That was a naive measurement using an “as the crow flies” buffer that, in reality, might have included areas that aren’t actually walkable (like a route between a specific bus stop and daycare center that is cut off by a highway).

I think about this problem every time I try to order food from my mom’s house. She lives on the side of a river before it opens onto a bay. There are only two bridges across the river (for a while there was only 1 several miles away). None of the takeout apps recognize that the restaurant a mile away directly across the river takes a half hour to drive to.

Another example we’ve lived through recently is how inaccessible a 1 mile buffer became for many people when the Key Bridge collapsed.

There are alternative ways to do these analyses that relate to travel. A common method is to build isochrones (time based) or isodistances (distance based), where you calculate the actual routes available from a starting point and then figure out the polygons accessible within some metric. Sometimes these are just locations in a street network accessible within 0.5 miles, 1 mile, 1.5 miles, and so on (or whatever set of distances you want). If you use a routing engine, you can do this for actual travel times by different modes of transit, such as a 5 minute drive, 10 minute drive, etc. There are some detailed examples in Lovelace et al. (2025) ch 13. For a more heavy-duty analysis you can run your own routing engine (I’ve done this with OSRM’s docker images) or use a paid service like Google or Mapbox, but for simple examples we can use free services for researchers like Open Route Service (requires an API key) or a few random demo servers you’ll find online (the osrm package will link you to one as its default). There are a few R packages that will do this and return sf polygons; here I’m using osrm.

Code 
courthouse <- sf::st_point(c(-76.6138131, 39.2907991)) |>
    sf::st_sfc(crs = 4269)

court_iso <- osrm::osrmIsochrone(
    courthouse,
    breaks = c(5, 7, 10),
    osrm.profile = "foot"
)

# save so I don't have to rerun in the cloud
saveRDS(court_iso, here::here("assets/courthouse_isochrone.rds"))
Code 
court_iso <- readRDS(here::here("assets/courthouse_isochrone.rds"))
# get a bbox around the isochrones for getting a basemap
court_bbox <- court_iso |>
    sf::st_transform(3857) |>
    sf::st_bbox()
toner_bg_terra <- basemaps::basemap_terra(
    court_bbox,
    map_service = "osm_stamen",
    map_type = "toner_bg",
    map_token = Sys.getenv("STADIA_TOKEN"),
    verbose = FALSE
)

ggplot() +
    tidyterra::geom_spatraster_rgb(data = toner_bg_terra) +
    geom_sf(
        aes(fill = forcats::as_factor(isomax)),
        data = court_iso,
        alpha = 0.8
    ) +
    scale_fill_manual(values = seq_pal) +
    coord_sf(ndiscr = 0) +
    labs(
        fill = "Walking time (mins)",
        title = "Where can I walk during jury duty lunch?"
    )

Of course, sometimes the distance we need isn’t connected to streets and travel. For example, the driving or walking route between your house and a major pollution source doesn’t matter, the distance does (and probably wind patterns). The EPA (still) considers living 300 feet from a major highway or other heavy transportation infrastructure to be a potential health hazard. That 300 foot buffer might be all the data we need for an analysis or visualization, or we might be interested in who or what is inside that buffer.

Mapping outside borders

Rasterizing / gridding data

Properly rasterizing data is outside the scope of this class, but we can do some simple experiments with making grids out of our data. (Lovelace et al. (2025) is a good read if you’re interested in more.) sf::st_make_grid creates a square or hex grid over some area, and you can join that with another dataset. You can create the grid based either on the number of cells or on the desired grid cell size.

Lovelace, R., Nowosad, J., & Muenchow, J. (2025). Geocomputation with R (2nd ed.).
Code 
balt_to_grid <- counties_sf |>
    dplyr::filter(name == "Baltimore city") |>
    sf::st_geometry() |>
    sf::st_transform(2248)

# for each grid, transform back to 4269 & make an sf data frame
# filter for only cells that intersect with city
# then give unique ID to each cell to aggregate
# supply n to set number of cells in each direction
balt_grid_20x20 <- balt_to_grid |>
    sf::st_make_grid(n = 20) |>
    sf::st_as_sf() |>
    sf::st_filter(balt_to_grid) |>
    sf::st_transform(4269) |>
    tibble::rowid_to_column("id")

# supply cellsize to set length of cells
balt_grid_05_mi <- balt_to_grid |>
    sf::st_make_grid(cellsize = 5280 / 2) |>
    sf::st_as_sf() |>
    sf::st_filter(balt_to_grid) |>
    sf::st_transform(4269) |>
    tibble::rowid_to_column("id")

balt_grid_20x20 |>
    sf::st_join(justviz::vacants_sf) |>
    dplyr::group_by(id) |>
    dplyr::summarise(n_vacants = dplyr::n()) |>
    ggplot() +
    geom_sf(aes(fill = n_vacants), color = "gray20", linewidth = 0.1) +
    geom_sf(data = balt_to_grid, fill = NA, color = "black") +
    scale_fill_fermenter(palette = "RdPu", direction = 1) +
    coord_sf(ndiscr = 0) +
    labs(
        title = "Count of vacants, aggregated to 400-cell grid, Baltimore city"
    )
Code 
balt_grid_05_mi |>
    sf::st_join(justviz::vacants_sf) |>
    dplyr::group_by(id) |>
    dplyr::summarise(n_vacants = dplyr::n()) |>

Densities / contours

Sometimes people call this a heatmap, I guess because it’s a map that’s often colored with red for the highest value, so it looks hot…? We’ve already made actual heatmaps and know those are a different type of chart. This is instead a contour map which models and smooths the locations in our data and/or their attributes using a kernel density estimate (KDE). Once again we have a few options of how to make this happen:

  • You can use ggplot’s built in geom_density_2d, which calculates a two-dimensional KDE with some parameters. You’ll do this with just the points’ coordinates, so you lose the spatial data and just treat the points as being in an XY cartesian plane. Fine for some situations, especially over a small area or where you don’t need to know actual distances or work with other spatial data.
  • There are a few packages that help build a spatial KDE.

First, the naive version:

Code 
# naive way with geom_density_2d:
# extract matrix of point coordinates, drop geometry column
# expand matrix out into 2 proper columns
vacants_xy <- justviz::vacants_sf |>
    sf::st_transform(2248) |>
    dplyr::mutate(coords = sf::st_coordinates(geometry)) |>
    sf::st_drop_geometry() |>
    dplyr::mutate(x = coords[, "X"], y = coords[, "Y"])

ggplot(vacants_xy) +
    geom_density_2d_filled(aes(x = x, y = y)) +
    geom_sf(data = balt_to_grid, fill = NA, color = "black") +
    scale_fill_brewer(palette = "RdPu", direction = 1) +
    coord_sf(ndiscr = 0) +
    labs(title = "Density of vacants")

Then the more refined version. The package spatstat (actually a collection of packages) is a general workhorse for spatial statistics. We need to convert our points to a spatstat point pattern object, and then we can get a density raster.

Code 
# following https://r-spatial.org/book/11-PointPattern.html
vacants_kde <- justviz::vacants_sf |>
    sf::st_transform(2248) |>
    # convert to spatstat point pattern data
    spatstat.geom::as.ppp(W = spatstat.geom::as.owin(balt_to_grid)) |>
    # calculate best bandwidth using cross validation
    # uses the generic density function but I want to make sure it's the right one
    spatstat.explore::density.ppp(sigma = spatstat.explore::bw.diggle)

# convert to a terra raster
vacants_rast <- terra::rast(vacants_kde)

ggplot() +
    tidyterra::geom_spatraster(data = vacants_rast) +
    geom_sf(data = balt_to_grid, fill = NA, color = "black") +
    scale_fill_distiller(
        palette = 'RdPu',
        direction = 1,
        na.value = "transparent"
    ) +
    coord_sf(ndiscr = 0) +
    labs(title = "Density of vacants")

There’s a lot more you could do with this (including making sure the whole city is covered), but this is just a starting point. This is one of the tutorials I followed to help debug this section.

Dot density map

Last alternative we’ll try is the dot density map. A dot density map is a type of thematic map where instead of shading polygons, you fill in each space with randomized dots to represent your data. Generally this will be populations, so you might have one dot per person, or one dot per 100 people, or something to that effect. Most famously these have been done by race/ethnicity across different cities or the whole country.

To be more accurate, I usually like to do these with block-level data, which you only get from the decennial census (every 10 years). A few packages create randomized dots for you, or you can calculate manually.

Generating the points for a dot density map is usually a pretty compute-intensive process: I used the dots package (the script is at misc_scripts/dot_density.R), switched to my heavy-duty laptop, and even with 48GB of RAM, only 2 variables, only Baltimore city, and scaling the counts by a factor of 5, it still took several minutes to calculate. That package doesn’t have an option for parallel processing, so for anything bigger than this I’d modify the package’s code or write the algorithm from scratch to work in parallel.

Code 
set.seed(1)
age_dot |>
    sf::st_transform(sf::st_crs(balt_to_grid)) |>
    dplyr::rename(age = dots_type) |>
    dplyr::mutate(age = forcats::as_factor(age)) |>
    # shuffle rows to make sure neither group blocks the other
    dplyr::sample_frac(size = 1) |>
    ggplot() +
    geom_sf(data = balt_to_grid, fill = NA) +
    geom_sf(aes(color = age), size = 0.25, alpha = 0.3) +
    scale_color_manual(
        values = qual_pal[c(1, 2)],
        guide = guide_legend(override.aes = list(size = 1, alpha = 1))
    ) +
    coord_sf(ndiscr = 0) +
    labs(
        title = "Population by age, Baltimore, 2020",
        subtitle = "Dot density estimated at block level"
    )
